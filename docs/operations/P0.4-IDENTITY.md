# P0.4 identity backend: implementation and operation

Updated: 2026-10-03. **Backend verified locally and in committed CI; no real-provider acceptance or production readiness claim.** The approved [Package A baseline](PACKAGE-A-RELEASE-GATE.md) remains distinct from this work. [ADR 0006](../adr/0006-identity-provider-and-session-policy.md) records the technical direction and commercial limits; [ADR 0007](../adr/0007-identity-security-boundaries.md) records persistence and audit boundaries.

## Actual implementation

`internal/identity` owns canonical authentication facts, explicit current permissions, Reader/Editor templates, a future step-up policy check and a vendor-independent OIDC adapter. Maintained OIDC/OAuth2/JOSE libraries perform protocol/signature work. Only configured HTTPS discovery/token/JWKS endpoints are allowed, with bounded responses, five-second network timeout and no redirects. The initial adapter accepts RS256 with suitable public RSA keys, verifies issuer, audience/authorized party, nonce, signature, token expiry and fresh signed authentication time. Keys are fetched for each exchange; no stale-key fallback exists. Unknown assurance remains UNKNOWN even if provider role/group/AMR fields appear. A real provider assurance mapping requires conformance evidence.

`internal/store` owns durable browser-bound login transactions, immutable issuer/subject mapping, hash-only session credentials and transaction-bound authorization. Provider-verified email admission creates an active internal User plus its mapping and bounded account-created evidence. It grants no Workspace, membership, role, SellerMandate or VerifiedClaim. No email is stored or used to link accounts. Disabled mappings cannot recreate/reactivate accounts.

`internal/httpapi` exposes JSON protocol/session endpoints and the existing workspace read/name-update commands. There is no HTML, frontend or configured hosted login screen. Exact bodies, response projections, cookies, errors and headers are in [OpenAPI](../../api/openapi/p0.4.json). Request IDs are server generated; client role, actor, owner and organization fields never establish authority. Unknown/case-variant/duplicate command fields and ambiguous credentials are rejected.

## Configuration

The API now requires `AUTHENTICATION_MODE` explicitly:

- `disabled`: health is available, all protected requests are denied; OIDC/PUBLIC_ORIGIN settings must be absent. This is an unavailable boundary, never a synthetic identity or authorization bypass.
- `oidc`: requires `PUBLIC_ORIGIN`, `OIDC_PROVIDER`, `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET`. Deliver the secret through controlled runtime secret injection, never Git or logs. `PUBLIC_ORIGIN` is an exact lowercase HTTPS origin without path; callback is exactly that origin plus `/api/v1/auth/callback`. `OIDC_ENDPOINT_ORIGINS` optionally lists at most four additional exact trusted HTTPS origins separated by commas. Discovery cannot select arbitrary network destinations.

The initial confidential client uses HTTP Basic token endpoint authentication, authorization-code/PKCE S256, scopes `openid email`, and `max_age=0`. It never requests `offline_access` or retains refresh tokens. Match these client settings in the eventual approved provider sandbox. New API startup requires successful provider discovery in OIDC mode. Already-running instances use local sessions for ordinary authorized operations during provider outage; new authentication still fails closed. Database uncertainty always denies access with a service error.

API and worker retain independent configuration/startup/shutdown. The worker has no OIDC dependency. Local health-only operation uses the Package A setup plus `AUTHENTICATION_MODE=disabled`; no insecure HTTP login mode exists. Test protocol transport injection is unexported and confined to the identity package's tests.

## Session policy enforced

Session credentials contain 256 random bits, sent only as `__Host-marketplace-session`, Secure, HttpOnly, SameSite=Lax, Path=/, without Domain or persistent-cookie lifetime. PostgreSQL stores their SHA-256 digest and a separate internal session ID. Absolute expiry is eight hours from verified authentication; idle expiry is fifteen minutes from the last committed successful workspace operation. Session introspection (`GET /api/v1/session`), public/failed requests and health checks deliberately do not extend idle time. This clarifies “accepted protected request” in the proposal and prevents background identity polling from keeping access alive.

Both expiry kinds require a new interactive authentication flow. Its start time is database-generated, browser binding/state are single-use, and protocol state expires after five minutes. `auth_time` must be at least flow start minus sixty seconds and no later than current time plus sixty seconds. Local expiry has no skew grace. Provider exchange failures consume the flow; start again, never replay it. Successful same-user authentication rotates credentials and atomically revokes an old supplied session. A previous session belonging to another user is rejected; log out before switching accounts.

Every protected workspace transaction checks account, session, current membership and current permission, holding locks through its read/write, audit/outbox and successful idle refresh. Account locking precedes session locking; revoke-all and disable serialize at the account. A command ordered before revocation may finish; subsequent commands fail. Permissions are never cached in cookies or provider metadata. Organization membership and managing ownership remain insufficient for workspace access.

`POST /api/v1/session/logout` revokes the current local session. `POST /api/v1/session/revoke-all` increments account security version and revokes all local sessions. Both require exact Origin, session-bound CSRF proof and a strict empty JSON object; state and security evidence commit atomically. Independent device sessions are allowed. These endpoints do not claim to terminate provider SSO. External password/account changes, provider logout notifications and reconciliation are not connected in this delivery. Their residual local-session window lasts until local revocation/expiry; provider outage does not shorten it.

The account-disable SQL primitive is unavailable to API and worker roles. Only the existing privileged migration/operator boundary can invoke it, attributed as an identity-operator service. It is not a staff access policy, administrative UI or delegated account-management API. A separately approved operational identity is required before real use.

## Browser and abuse boundary

Login start is same-origin POST with `{}`. It returns a protocol authorization URL and a five-minute HttpOnly browser-binding cookie. Callback consumes the exact state/binding before exchanging the code. It returns an allowlisted session projection, never provider claims or a token in JSON/URL. No caller-supplied return redirect is accepted.

Unsafe authenticated requests require exact Origin and `X-CSRF-Token`. The proof is SHA-256 of a domain-separated high-entropy session credential, returned only in a same-origin no-store session response. It cannot authenticate alone. There is no permissive CORS. Credential cookies, Authorization headers and body fields are parsed strictly. Existing CSP, no-store, nosniff, referrer and frame protections apply. TLS termination/trusted ingress remain deployment controls; no production ingress was provisioned.

PostgreSQL admits at most 120 new login flows per database-clock minute and cleans expired transient flows during admission. No IP/device fingerprint is stored. This bounds persisted protocol state, but an attacker can exhaust the global budget. Account-aware credential stuffing/recovery defenses belong to the selected provider and edge controls, which remain unverified. Expired rows may remain until the next admission; there is no claim of a scheduled erasure service.

## Migration, audit and recovery

Apply new `000002_identity_sessions.sql` using the existing migration role after reviewing its checksum. Never edit applied `000001_package_a.sql`. It adds account security version, issuer/subject mappings, login/admission/session tables, service principals, typed security evidence, worker receipt attribution and session-aware authorization. Constraints prevent mismatched session/user mappings and invalid actor shapes. Runtime roles have narrow security-definer function access, not direct identity-table writes or security-ledger mutation.

Historical workspace `audit.events` remains tied to its existing outbox constraints and explicitly HUMAN. New `audit.security_events` records account creation, session creation/current/all revocation and account disable with typed derived actor, target, timestamp, request/correlation IDs and fixed result; metadata is exactly `{}`. Existing material workspace state/audit/outbox commit together. Session lifecycle changes use atomic security evidence; there is no fake asynchronous event for an absent consumer. Ordinary anonymous probes, routine workspace denials and unimplemented elevated operations do not generate an unbounded durable ledger. Sensitive future operations must add their own bounded denial schema.

Consumer receipts retain at-least-once idempotency and identify the outbox-worker SERVICE actor separately from the human initiating the workspace event. The worker cannot authenticate as a human or use identity functions.

An unknown COMMIT outcome is an error, not success or a reason to bypass checks. A failed login completion may have created an inaccessible session: discard the unsent raw credential, begin a new flow, and let the bounded session expire. Retrying a workspace mutation requires rereading its version. No automated schema downgrade or data-erasing rollback is supplied. Migration two changes protected-command assumptions, so deploy coordinated API/worker binaries with the additive migration; do not roll back to the pre-session API while treating P0.4 guarantees as intact.

## Scope, assets and trust boundaries

In scope are Go authentication adapters, a canonical human/service principal, PostgreSQL login transactions and application sessions, the existing workspace read/name-update commands, current-session/all-session revocation, bounded security audit and independently runnable worker attribution. Credentials, external identity mappings, session hashes, account security state, membership, permissions and durable evidence are protected assets. Login transaction secrets are transient security material even though their lifetime is short.

Out of scope are password verification/recovery implementation, provider provisioning, invitations, account linking, staff impersonation, marketplace screens, listings, seller-mandate verification, payment or document workflows, and AWS infrastructure. The authentication boundary must preserve the ability to implement future step-up without pretending an elevated workflow already exists.

| Boundary | Untrusted input or assertion | Required enforcement |
| --- | --- | --- |
| Browser to HTTP adapter | Cookies, code/state, Origin, requested workspace, body and headers | Bounded requests; strict credential/parameter parsing; server-generated request context; exact Origin and CSRF proof for unsafe authenticated operations; no client actor/role authority |
| Go to configured identity provider | Discovery, endpoints, signing keys, token response | Fixed configured issuer, trusted HTTPS network policy, bounded time/bytes and redirects; maintained signature implementation; strict protocol validation; no dynamic browser-selected issuer |
| External identity to principal | Issuer/subject, verified email and assurance evidence | Translate once; immutable internal identity; no email linking or permissions from provider roles/groups; disabled accounts stay disabled |
| HTTP authentication to protected command | A session that may be revoked concurrently | Revalidate session, account and current authorization inside the command transaction; authentication middleware is not the final authorization decision |
| One workspace to another | Resource IDs and organization relationships | Explicit active scoped membership and permissions; unchanged organization non-bypass; RLS as an additional defense |
| API to PostgreSQL security state | Session creation, revocation, audit and business mutation | Narrow runtime capabilities, database constraints, deliberate lock order, atomic critical state/evidence and no bypass using supplied User IDs |
| Worker process to audit/effects | Machine actor identity and at-least-once events | Service actor distinct from human User; scoped process capability; durable duplicate handling; no human impersonation |
| Runtime to telemetry/audit | Error text and event context | Allowlisted safe codes and structured fields; no credentials, token responses, state/nonce/verifier, request bodies or arbitrary personal strings |

The configured provider and application runtime are trusted components, not equivalent to a trusted browser. A compromised migration identity/database administrator can change the system's trust state; runtime least privilege does not make the ledger immune to privileged tampering.

## Security decisions to verify in source

Use the policy in ADR 0006 as the source of session/admission values. Its intended session is a random 256-bit opaque credential with only its hash persisted, eight-hour absolute expiry measured from evidenced interactive authentication, and fifteen-minute accepted-request idle expiry. Database time governs local expiry; browser time cannot extend it. No provider refresh token or persistent remember-me mode is introduced.

A successful login creates a new application credential. Concurrent first admission is unique by issuer/subject and must not recreate a disabled account. Implemented rotation rejects a previous browser session belonging to a different internal user and rolls back the new admission; switching accounts requires logout first. It does not revoke that other user's credential or attribute a foreign revocation to them. Failed callback/exchange does not restore a consumed login transaction. The caller starts a fresh bounded flow instead.

The planned CSRF proof is a domain-separated SHA-256 derivation from the random application credential, supplied only by the authenticated no-store session response. The proof is not an authentication credential: possession without the valid cookie grants nothing. Constant-time comparison, exact configured Origin, rejection of missing/null Origin on unsafe operations, no cross-origin credential access, and strict cookie parsing are separate controls. A sibling subdomain being same-site does not satisfy exact-origin validation. OWASP recommends session-bound proofs and origin validation; the particular derivation is an application design choice, not a claim that OWASP specifies this encoding. [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

For every protected command, lock account/security state before the session and then workspace membership/permissions/resource in a consistent order. Session revoke-all, account disable and login/rotation must agree on that ordering. Recheck expiry using current database time after lock acquisition, since the transaction may have waited. An accepted operation may extend idle time only inside the transaction that accepts it; denial, invalid input, missing resource or failed commit must not refresh the session. A command already serialized before revocation may complete. Subsequent operations must fail; retroactive cancellation is not promised. PostgreSQL row locks serialize conflicting changes but inconsistent acquisition order can deadlock, so concurrency tests are essential. [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)

The successful login/session response cannot manufacture a Workspace, membership, permission, SellerMandate or VerifiedClaim. Email-control evidence is not evidence of legal identity or authority to sell. Only existing workspace.read and workspace.update are required; roles resolve to scoped grants, without future capability names or organization-wide shortcuts.

Session introspection is deliberately read-only: GET /api/v1/session and middleware resolution do not extend idle expiry. Only successfully committed protected workspace read/update operations advance accepted activity. A polling client cannot keep a session alive merely by inspecting it. Logout ends the relevant credential rather than refreshing it. The contract and tests must distinguish this from a claim that every authenticated HTTP response extends activity.

Source review on 2026-10-03 confirmed that production workspace commands receive a session hash and derive the User inside their transaction; the old arbitrary ActorID adapters are confined to test binaries. Migration 000002 uses a composite issuer/subject/User foreign key for sessions, narrow function grants with fixed search paths, a fixed identity-operator service attribution for the owner-only disable primitive, and separate security evidence. API and worker roles cannot invoke the operator primitive. Security-event session/target attribution has a composite foreign key and current human actions are constrained to self-service. Worker composition establishes its canonical SERVICE principal after validating its database capability; receipt attribution is constrained to that service. These are inspected implementation observations; they do not replace execution evidence below.

## Abuse cases and required evidence

This matrix states required evidence, not a blanket pass. The focused local evidence below covers implemented checks; unavailable provider, UI and operational evidence remains unperformed. A test name or code review alone is not a passed result. The eventual verification report must record exact commands, commit, artifacts and clean-checkout CI result, with real PostgreSQL for database semantics.

| ID | Threat or failure | Required prevention and negative evidence |
| --- | --- | --- |
| I01 | Forged, unsigned, wrong-key, wrong-issuer/audience/authorized-party or unexpected-algorithm identity token | Reject before principal mapping or session creation; do not accept unsigned/development credentials; test invalid signature, algorithm, audience, issuer and ambiguous credentials |
| I02 | Expired credential, stale/missing auth_time or manipulated clock | Reject expired/unverifiable facts; external skew capped by policy; database expiry has no grace; test exact expiry boundaries, missing freshness and clock values beyond permitted skew |
| I03 | Login CSRF, code injection, replay or parallel callback | Single-use browser-bound state, nonce and PKCE S256; strict duplicate code/state parsing; test foreign/missing binding, nonce mismatch, replay, concurrent consume and provider error callback; provider exchange failure cannot revive state |
| I04 | Session fixation or cross-user rotation | Random fresh credential, Secure/HttpOnly/SameSite cookie, no token in URL/body; old same-user credential revoked atomically; test old-cookie rejection and a foreign previous cookie cannot revoke an unrelated user's session |
| I05 | Stolen session or CSRF proof | Hash-only durable session credential; no token logs/browser storage; proof alone is not authentication; test token/proof separation and cookie attributes; acknowledge bearer theft permits requests until expiry/revocation |
| I06 | Cross-site mutation/logout or sibling-site request | Exact Origin plus session-bound proof, no unsafe GET, no permissive CORS; test absent/null/foreign Origin, wrong/absent proof, duplicate cookies, unexpected Authorization header and wrong method |
| I07 | XSS-assisted token theft or authenticated use | No HTML/template output from the identity backend, restrictive headers, no-store, credentials HttpOnly; output allowlists and log canaries; later UI needs escaping/CSP/accessibility review; HttpOnly does not stop malicious same-origin script from issuing requests |
| I08 | Open redirect, provider mix-up or SSRF | Exact issuer/callback and bounded configured endpoints; no caller-controlled return URL or key fetch URL; test untrusted discovery/JWKS/token endpoint, redirects, protocol downgrade, oversized response and cancellation |
| I09 | Account enumeration, duplicate first admission or unsafe linking | Generic authentication failure, unique issuer/subject mapping, no email merge, no inactive-account reactivation; test unverified email rejection, concurrent admission, existing inactive mapping and equivalence of public account-failure responses |
| I10 | Credential stuffing or weak recovery | Credentials/recovery delegated to reviewed provider; no local password cryptography; login admission bounded in PostgreSQL; test limiter and failure behavior; actual provider abuse/recovery controls remain a real-provider acceptance gate |
| I11 | Stale session after local logout, revoke-all or account disable | Authoritative DB check on every protected transaction; atomic revocation/security audit; test current/all-session revoke, multiple devices, security-version mismatch, disabled account, lock ordering and requests racing revocation |
| I12 | Failed requests prolong session or expiry passes during lock wait | Idle touch commits only with accepted protected operation; current DB time checked after waiting; real PostgreSQL tests prove denial/rollback do not touch idle and an expired waiting request cannot enter |
| I13 | Tenant hopping or guessed identifiers | Server-selected permission and DB-derived user; same not-found behavior for unknown/inaccessible resources; negative HTTP/store tests for read and mutation across workspaces, path substitution and direct SQL defenses |
| I14 | Client role/owner/organization fields or provider groups elevate access | Strict allowlisted body/contracts; actor from validated session; unknown fields rejected; tests ignore/reject client role/actor/permission assertions and provider group claims without granting authority |
| I15 | Organization membership or ownership bypass | No automatic workspace grants; current scoped permission lookup; preserve Package A negative tests for organization membership/owner without explicit workspace access and revoked grants |
| I16 | Permission revoked concurrently or pooled tenant context reused | Lock current membership/permission rows through transaction; SET LOCAL scope only; real PostgreSQL races and pool reuse tests prove no stale-session grants or tenant context leakage |
| I17 | Confused deputy or service actor masquerades as human | Typed human/service model and capability-specific execution; no universal worker token or human User fixture in production; test actor invariants, worker/API role separation and audit actor attribution |
| I18 | Audit spoofing, sensitive payload dump or audit-write failure | Server-derived actor/request context and bounded action/metadata schema; immutable historical attribution; state+required evidence commit atomically; test fake actors, forbidden metadata and injected audit failure rolling back state |
| I19 | IdP/JWKS outage or PostgreSQL failure | New authentication/elevation fails closed; known valid local sessions follow explicit outage policy; missing credentials 401, permission denial 403 where safe, inaccessible resource 404, dependency uncertainty 503; test each distinct failure without development fallback |
| I20 | Provider-side password/block/revoke leaves local access | Separate local from external revocation semantics; authenticated replay-safe provider events/reconciliation require selected-provider proof; test what exists and explicitly mark absent provider integration, propagation monitoring and residual delay |
| I21 | Missing assurance treated as MFA or future step-up bypass | Assurance evidence and source explicit; absence/unknown denies elevation; role/email/group is not MFA; test human/service distinction, fresh/stale evidence, unsupported methods and future five-minute freshness policy without adding product operations |
| I22 | Authentication request floods, unbounded transient rows or lock contention | Bounded request/body/response/time, global admission limiter and bounded expired-login cleanup; test rate budget/concurrency, database failure and no indefinite resource growth; global budget exhaustion remains an availability risk requiring edge/provider controls |
| I23 | Secrets escape through errors, HTTP access logs, SQL diagnostics or CI | Safe fixed route/error codes; no query strings, cookies, provider body or connection string in logs; sentinel tests and secret scans; scan coverage and finding count must be recorded |
| I24 | Migration changes historical attribution or loosens existing workspace/outbox constraints | Additive reviewed migration, existing ledger/checksum retained, Package A fixture upgrade plus fresh schema, runtime privilege tests, backward evidence checks; existing atomic outbox/receipt/rollback cases remain required |

Authorization-code flow, PKCE, redirect validation and replay controls are based on the [OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html). The adapter must enforce the relevant signed identity-token claims rather than treating a decoded JSON object as authenticated evidence. [OIDC Core token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)

## Durable evidence boundary

Application logs are operational evidence, not the audit ledger. Authentication/session lifecycle changes require deliberately structured security events. Existing workspace name changes retain state/audit/outbox atomicity. An asynchronous event is required when an external or deferred effect exists; adding a session does not justify inventing a fake external consumer.

Audit actors must distinguish HUMAN and SERVICE. A service has no fabricated human User ID. Preserve pre-P0.4 workspace audit rows and the outbox's existing relationship to their workspace/resource version. If security events use a distinct constrained relation, its structured attribution and append-only runtime permissions require the same tests. A denial record intentionally written outside a rolled-back business transaction must have an explicit bounded policy; do not produce an unbounded durable event for every anonymous probe.

The current security ledger records successful account.created, session.created, session.revoked, sessions.revoked and account.disabled operations. Ordinary authentication, CSRF and workspace denial paths use bounded operational telemetry. No high-risk product or public administrator operation exists in this package, and no durable failed-elevation/sensitive-denial event is claimed. Such operations must define the required independent denial-audit path before they enter scope.

Audit and log metadata may include fixed action/reason codes, internal resource/session/principal IDs, server-generated request/correlation IDs, timestamp and result. Do not include raw tokens, credential hashes, authorization codes, CSRF proof, nonce, PKCE verifier, full provider claims, email, arbitrary user-agent strings, request body or document content. Subject mappings remain personal-data considerations even without an email column; pseudonymous does not mean anonymous.

## Residual risks and release conditions

- A stolen valid browser session remains usable until local expiry/revocation. HttpOnly and the CSRF proof do not neutralize malicious code executing in the allowed origin. Elevated future commands require their own assurance/freshness rules.
- The intended local-session outage policy deliberately permits ordinary authorized operations during provider outage until local expiry/revocation. Provider-side security changes are not instantly reflected merely because local logout is atomic. Real provider event coverage, entitlement, latency and reconciliation are unproven without an approved tenant and credentials.
- A global login budget limits persistence pressure but an attacker can consume the shared budget. It does not replace edge, provider or account-aware abuse controls. Traffic sizing and operational alert ownership are still required before deployment.
- No application password/recovery flow is implemented. Provider passkey, MFA, recovery, credential change, logout and disabled-account behavior must be validated in an approved sandbox; local signed-token fixtures prove adapter behavior, not vendor conformance.
- Privileged database/runtime compromise can forge authentication facts or alter grants. Process/database least privilege, secret protection, reviewed deployment and incident containment remain necessary. No staff override is introduced.
- Authentication state and audit need approved privacy purposes, retention, deletion/hold rules and operators before real-user use. Short-lived flow cleanup is a resource control, not a legal retention determination.
- Backend JSON contracts are not a researched authentication user journey. No Mobbin pass, hosted-screen customization, browser accessibility verification or visible interface is claimed. Fresh targeted research remains mandatory before any screen or visible hosted product journey is implemented.
- Deployment TLS termination, trusted ingress, secure secret delivery, backup/restore, clock monitoring, authentication alerting and incident response remain operational release gates. Source tests alone cannot prove them.

P0.4 must not be reported as fully verified until the relevant matrix cases have inspected test evidence and CI has run from the final committed source. Any real-provider test that cannot run must remain explicitly unperformed; it cannot inherit success from synthetic fixtures or Package A's older CI result.

## Authentication boundary and principal

An `Authenticator` resolves a verified application session; an OIDC adapter handles provider exchanges and translates external facts once. A `PrincipalResolver` maps the exact approved `(issuer, subject)` pair to an immutable internal principal. Provider group/role/custom permission metadata is not application authority. Never link accounts by matching email addresses, and never accept an issuer supplied by the browser.

The canonical principal contains `PrincipalID`, `ActorKind` (`HUMAN` or `SERVICE`), optional human `UserID`, approved provider identifier and subject, authentication time when evidenced, internal session ID where applicable, and an explicit assurance value with its evidence source. Request and correlation IDs are separate server-generated context. Unknown assurance stays unknown; `email_verified` establishes only the provider's email-control claim, not identity verification or authority to sell. Raw tokens/claims do not cross into marketplace rules.

Use authorization-code flow with PKCE S256, one-time browser-bound state and nonce, an exact registered callback and server-side token exchange. Only configured HTTPS endpoints may be fetched, with bounded response size/time and no redirect to unapproved hosts. Verify signature, approved algorithms, issuer, audience/authorized party, nonce, expiry and relevant authentication time. Reject unsigned tokens, unknown algorithms, duplicate/ambiguous credentials and untrusted key URLs. Provider key rotation may use a bounded trusted cache; unknown keys cannot be accepted during an outage. These choices follow [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) and [OIDC Core validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation).

## Proposed session policy

These are proposed product/security choices, not claimed mandatory standard values. Server-side expiry and renewal follow the principles in the [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

| Concern | Proposed behavior |
| --- | --- |
| Browser credential | Cryptographically random 256-bit opaque token, hash stored in PostgreSQL; `__Host-` cookie, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Never localStorage or URL tokens. An internal non-secret session ID identifies audit records. |
| Absolute lifetime | Eight hours from the provider-verified interactive authentication; activity never extends this deadline. No persistent remember-me mode. Reject an exchange that cannot establish required fresh authentication time. |
| Idle lifetime | Fifteen minutes since the last accepted protected request, enforced atomically by the database clock. Public browsing and failed requests do not keep a session alive. |
| Renewal/refresh | No `offline_access` and no provider refresh-token persistence initially. Expiration requires a new validated authorization flow. Provider SSO must not silently reset the application's interactive-authentication deadline. Provider tokens remain server-side only for the bounded exchange and are then discarded. |
| Fixation/rotation | Create a fresh application token after authentication and step-up; revoke the previous token as part of the same durable operation. Concurrent rotation must not resurrect an old session. No rolling periodic rotation is needed for this initial bounded session policy. |
| Local revocation | Check active session and account security version for every protected operation. Logout/revoke/account-disable commits an intentional security audit event atomically; later protected operations fail. A command already authorized inside a transaction is ordered against revocation by locking, rather than promised retroactive cancellation. |
| Logout | CSRF-protected POST invalidates the current application session even when provider logout fails. Provider and application logout are distinct. Provider logout errors are observable; a browser redirect does not prove all upstream sessions ended. |
| Multi-device | Independent session per device/login. Allow current-session and all-session revocation through authenticated backend contracts. No workspace rights are attached to a device cookie. |
| Credential/recovery change | Application-initiated security changes revoke all local sessions before reporting completion. Provider-initiated events require authenticated, replay-safe back-channel/event integration and reconciliation. Do not claim immediate revocation for an eventually consistent provider event. |
| Account disable | Application disable is authoritative at the next serialized authorization check. Provider-side disable is separate: its notification/reconciliation path, failure behavior and residual delay must be proven against the selected provider before real-user acceptance. |
| Clock skew | At most 60 seconds of configured tolerance for external token timestamps, with issuer/server clock monitoring. Database session expiry itself receives no browser-controlled skew or grace. Missing or implausible authentication time cannot establish recent authentication. |
| Session theft | Hash-only persistence, TLS/cookie controls, CSRF checks, no credential logs, explicit revocation and fresh assurance for elevated operations. Neither HttpOnly nor idle expiry prevents an attacker who already holds a valid session from issuing requests. |
| Dependency outage | New login, key retrieval and elevated verification fail closed if verification cannot be completed. Existing locally valid sessions may perform ordinary currently authorized operations until local expiry/revocation; this intentionally means provider outage alone does not invalidate all application sessions. Provider-event delay is a stated residual risk, not an immediate revocation guarantee. Database/session/authorization uncertainty returns a service error and grants no access. |

The eight-hour absolute/fifteen-minute idle proposal is intended for the initial workspace boundary. Sensitive future capabilities require their own freshness/assurance policy. An available SSO cookie is not proof of fresh credentials; request fresh authentication and validate the returned facts. [OIDC authentication age](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)

## Authorization and workspace policy

Resolve principal, requested resource, requested workspace and required permission on the server. Keep the existing `workspace.read` and `workspace.update` permissions; update also requires read. Do not populate unused listing/billing/member permission names. Proposed role templates are Reader (read) and Editor (read/update), resolved to explicit workspace grants. Roles cannot manufacture a membership, ownership, mandate or verification claim. Role-template edits must have explicit propagation/version semantics before enabled; no silent retroactive expansion.

Membership and permission changes remain authoritative in PostgreSQL with no session-embedded permission cache. Preserve Package A's transaction-local context, negative RLS tests and revocation ordering. User-controlled workspace, organization, owner and role inputs select requested context only. Missing credentials produce 401; authenticated failure to perform an exposed known operation produces 403; inaccessible resource identifiers retain a uniform 404 policy to avoid disclosing existence. Dependency failure is 503, not a fabricated 401/403.

Organization membership never automatically grants every organization workspace. Future broker UX can apply a reviewed role template to explicitly selected client engagements in one audited operation, including a preview of the affected workspaces. Persist the resulting scoped grants, show understandable engagement names and support clear revocation. Do not make a broker operate raw ACLs one at a time, and do not weaken tenant checks to achieve simpler UX. Bulk delegation UI/commands, invitations, ownership transfer and last-owner rules remain separately reviewed work.

## Separate authority, verification and machine actors

`AuthenticatedPrincipal`, `OrganizationMembership`, `SellerMandate` and `VerifiedClaim` remain distinct concepts and persistence responsibilities. No login callback or email-domain match creates mandate/verification rows. The future mandate contract must name the represented party, sale context, permitted actions, evidence/process, validity and revocation; no legal conclusion or live mandate workflow is introduced here.

The principal/audit model supports a service actor with its own identifier and credential provenance. A worker uses process-bound service identity and its existing database capability, never a fabricated human session or User. No public machine-login endpoint, reusable universal service token or organization-wide bypass is added. Future workload credentials and delegation are separately verified adapters.

Step-up policy consumes explicit assurance and authentication age, not an `admin` role check. Proposed freshness window for a future elevated command is five minutes with a configured acceptable method. Missing/unsupported assurance denies elevation. P0.4 tests the mechanism; it does not enable binding offers, billing changes, sensitive document grants or administrative override.

## Security audit and failures

Add typed actor references and bounded security-event schemas through new reviewed migrations while preserving historical Package A attribution. Record security-relevant session creation, revocation, account disable, effective membership/permission changes and failed elevated operations; successful material mutations remain atomic with their audit/outbox records. Persist sensitive authorization denials on an intentionally bounded path outside the rolled-back business transaction. Harmless anonymous requests produce rate-limited operational telemetry, not an unbounded personal-data ledger.

Never store raw credentials, provider token bodies, nonce/verifier values, arbitrary user-agent strings or request payloads in audit metadata. Account/provider subject references are personal-data considerations under D08; real-user deployment and retention/deletion automation remain gated. Authentication errors are generic to callers while safe internal codes distinguish verification failure, dependency outage and authorization denial.

## Threat review and required evidence

| Threat | Planned mitigation / evidence |
| --- | --- |
| Theft, replay, fixation | Hash-only sessions; fresh rotation; one-time state/code flow; nonce/PKCE; replay and parallel callback tests; document bearer-theft residual risk. |
| Stuffing, enumeration, recovery | Provider-managed credentials and recovery; generic application responses; provider/edge and application abuse limits; no local password cryptography or email-only account linking. Test provider failure and account-existence response equivalence. |
| CSRF and XSS-assisted use | Exact allowed Origin plus session-bound CSRF proof on mutations/logout, cookie policy and no unsafe GET changes; safe headers/output and no tokens in browser storage. XSS can still operate an active session, requiring prevention and step-up. |
| Open redirects, SSRF, forged claims | Exact configured issuer/callback/return-path allowlist; bounded trusted endpoint fetches; strict JWT verification; malicious issuer/key URI/audience/algorithm/nonce tests. |
| Stale authorization, privilege escalation, tenant hopping | Current application grants and account/session state; organization non-bypass; read/update negative tests; concurrent revoke/command ordering; client headers/body cannot supply authority. |
| Confused deputy and audit spoofing | Distinguish human/service actors; scoped capabilities; server-built audit context; validated provider event identity and replay protection; service actor cannot claim a human User. |
| Clock manipulation and provider outage | Server/database time; bounded external skew; reject unverifiable freshness; no development fallback; outage policy tested for new login, ordinary sessions and elevated operations separately. |
| Provider-side revocation delay | Local security commands revoke immediately under transactional ordering; provider event processing is authenticated/idempotent and observable. Exact provider propagation limits remain a live-conformance and owner-acceptance gate. |

Before completion, run all Package A gates plus malformed/invalid/expired credentials, unsigned/wrong-key/wrong-issuer/audience tokens, valid principal mapping, disabled/revoked sessions, cross-tenant access, organization non-bypass, forged role/workspace context, concurrent requests/revocation, audit attribution and outage tests. Use actual PostgreSQL for sessions/migrations/atomicity. External-provider fixtures test faults; they do not alone prove the selected vendor integration. A real approved sandbox must prove issuer/key rotation, chosen methods, freshness/assurance, logout, password recovery and revocation behavior. Report each unperformed check honestly and require CI from the final committed code.

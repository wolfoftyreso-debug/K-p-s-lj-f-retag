# P0.4 identity provider options

Date: 2026-09-24. Status: **PROPOSED — D03 owner decision required; no provider selected, account created, contract accepted or integration verified.**

The user confirmed that no provider has been chosen and requested a proposal. This research follows the Package A CI gate. It is not an implementation approval for unresolved session, privacy or supplier policy. Evidence below is current official documentation, not a test of an actual tenant. No authentication interface or Mobbin research is claimed.

## Recommendation

Prefer **Auth0 in its EU public-cloud locality** with a standard Go OIDC adapter and application-owned PostgreSQL sessions. The preferred configuration includes **an Enterprise entitlement for OIDC back-channel logout and session management**, subject to an acceptable quote, processing terms and a successful synthetic-data sandbox evaluation. The reason to consider that entitlement is the concrete ability to propagate provider-session termination to local sessions and inspect provider session state, not the phrase “enterprise grade.” This is an engineering judgement, not a claim that Auth0 is cheapest or that an EU tenant guarantees EU-only processing.

Do not select a cheaper plan silently if the required features are unavailable. Bring the choice back with an actual quote and the changed security trade-off. No spending or provisioning is authorized by this document.

| Option | Fit for this foundation | Main constraint | Decision |
| --- | --- | --- | --- |
| Auth0 EU, required Enterprise features | Managed credentials, OIDC, database-connection passkeys, step-up and documented session termination integration | Enterprise entitlement/budget; asynchronous propagation; provider configuration and claims need real tenant proof | Preferred, conditional on owner acceptance and proof |
| Auth0 EU, lower plan with the necessary login/MFA features | Same application-owned OIDC/session boundary; local disable and logout remain immediate after their database commit | No assumed back-channel or provider session API entitlement; provider-side changes can leave local sessions usable until local expiry/reconciliation | Viable if the owner accepts the explicitly weaker propagation policy; verify actual plan features |
| Amazon Cognito user pools | Managed identity aligned with the chosen AWS platform; viable password/passkey/MFA path | Different session/revocation semantics and unproven assurance mapping require more adapter-specific work | Credible alternative if Auth0 commercial terms are unsuitable |
| Self-hosted Keycloak | Configurable OIDC, passkeys, step-up and session controls; deployment-location control | Team owns identity availability, patching, credentials database, backups, recovery and configuration security | Reconsider if supplier/control requirements justify operating it |

A lower-plan/Cognito design can use a short hard application-session lifetime, fresh OIDC authentication on expiry, immediate application-owned disable/revocation, and no refresh-token persistence. This bounds the lifetime of an already-issued **local** session; it does not promise a fixed provider-revocation delay because provider consistency, in-flight authentication and credential-change effects still require proof. Provider-only changes may leave a session usable until expiry. Requiring frequent reauthentication also costs user time. If this trade-off is accepted and no near-real-time provider-session notification is required, purchasing back-channel support solely for architecture prestige is not justified. Obtain a quote and choose the required propagation policy together; no price or automatic purchase approval is assumed.

## Auth0 evidence and constraints

Auth0 documents an EU locality with EU sub-localities; sub-locality placement cannot be manually selected. Separately confirm contract, subprocessors, operational/support access, telemetry, backups and email delivery before processing real data. A hosting-region setting is not a legal residency assurance. [Tenant regions](https://auth0.com/docs/get-started/auth0-overview/create-tenants)

OIDC back-channel logout uses a provider session identifier and signed logout tokens. It requires an Enterprise plan and a provider-reachable TLS callback. Delivery is queued and eventually consistent, so it cannot promise instantaneous revocation. Validate issuer, audience, signature, token purpose, time and session binding; process repeats idempotently. [Back-channel logout](https://auth0.com/docs/authenticate/login/logout/back-channel-logout)

Select termination initiators explicitly: relying-party/provider logout, password change, session expiration/revocation, account deletion and email-identifier change. The documented list does **not** establish a user-block event; do not equate blocking future sign-in with invalidating local sessions. Use application-owned disable/revoke commands and document reconciliation of provider-only administration. [Initiators](https://auth0.com/docs/authenticate/login/logout/back-channel-logout/oidc-back-channel-logout-initiators), [blocking users](https://auth0.com/docs/manage-users/user-accounts/block-and-unblock-users)

Enterprise session-management APIs can inspect and delete sessions. Deletion is asynchronous; refresh tokens may outlive the provider session. Neither deleting provider sessions nor revoking refresh tokens substitutes for revoking application sessions. Measure the propagation window and failure behavior in the sandbox. [Session APIs](https://auth0.com/docs/manage-users/sessions/manage-user-sessions-with-auth0-management-api)

Database connections support passkeys and Universal Login. Initial email-identifier/password authentication can evolve to passkeys without accepting passwords into the marketplace backend. Select the long-lived login domain/RP ID before real passkey enrollment; domain changes can invalidate existing enrollments. MFA factor availability depends on the plan. Require user verification for the intended high-assurance WebAuthn path and verify the actual resulting claims. [Passkeys](https://auth0.com/docs/authenticate/database-connections/passkeys), [WebAuthn MFA configuration](https://auth0.com/docs/secure/multi-factor-authentication/fido-authentication-with-webauthn/configure-webauthn-security-keys-for-mfa)

An `amr` value containing `mfa` can evidence the documented completed MFA flow. Auth0 warns that silent/refresh-issued ID tokens may omit `amr`; omission must never be promoted to assurance. Step-up must bind a new authentication transaction to the same subject and verify both freshness and approved assurance evidence. `auth_time` from a federated upstream can describe an exchange rather than fresh credential entry, so initially defer social/enterprise federation. [Step-up claims](https://auth0.com/docs/secure/multi-factor-authentication/step-up-authentication/configure-step-up-authentication-for-web-apps), [reauthentication constraints](https://auth0.com/docs/authenticate/login/max-age-reauthentication)

## Cognito evidence and constraints

Cognito now documents passkeys with user verification satisfying required MFA when `FactorConfiguration` is `MULTI_FACTOR_WITH_USER_VERIFICATION`. The older blanket assertion that Cognito passkeys and MFA are incompatible is no longer accurate. Email/SMS OTP first-factor sign-in remains incompatible with required MFA. The MFA page also contains an adjacent choice-based sign-in limitation that requires clarification in the exact configured flow; do not resolve that ambiguity by assuming behavior. [Authentication flows](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-authentication-flow-methods.html), [MFA configuration](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa.html)

The documented default ID token has `auth_time`, `token_use`, issuer, audience and subject; it does not establish an `acr`/`amr` assurance contract for the proposed flow. Treat this as unproven, not as proof that these claims can never be provided. Never infer MFA from a user preference or group. Managed login has a one-hour cookie separate from token expiry. [ID-token contract](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-id-token.html)

Revoked Cognito JWTs still pass ordinary local signature/expiration checks. A production integration needs a separately proven revocation/disable signal and bounded stale-state policy for application sessions. Managed logout also does not terminate upstream OIDC/social sessions. [Revocation](https://docs.aws.amazon.com/cognito/latest/developerguide/token-revocation.html), [logout](https://docs.aws.amazon.com/cognito/latest/developerguide/logout-endpoint.html)

AWS documents regional profile storage and optional cross-region processing paths. Verify the chosen pool, email, analytics, replication, logs and contractual settings together; do not choose an AWS region from the owner's location. [Regional data considerations](https://docs.aws.amazon.com/cognito/latest/developerguide/security-cognito-regional-data-considerations.html)

## Keycloak evidence and constraints

Keycloak documents passkeys, configurable authentication levels, OIDC step-up, session controls and back-channel logout. Map assurance to reviewed flows, not arbitrary role names. Its SSO/client idle and maximum lifetimes are distinct, and refresh requests can renew provider idle activity; application idle expiry must remain independent. Existing access tokens are not made safe merely by clearing an SSO session. [Administration guide](https://www.keycloak.org/docs/latest/server_admin/)

Operating Keycloak would add an identity runtime and credentials store with availability, patch, restore, key-rotation and incident obligations. Its availability documentation is useful design input, not a mandate to introduce Kubernetes. A local Keycloak test instance could test protocol interoperability but would not prove an Auth0 or Cognito adapter. [Availability guidance](https://www.keycloak.org/high-availability/introduction)

## Common integration proposal

Use authorization code flow with PKCE, one-time state/nonce and strict redirect allowlists. Exchange and validate tokens only on the Go server. Translate allowlisted facts once to an internal principal keyed by immutable application user ID and the exact issuer/subject pair. Never link accounts automatically by email; email control is not seller authority. Provider roles, groups and organization claims confer no application permissions.

Prefer an opaque Secure/HttpOnly browser cookie backed by PostgreSQL; store only a digest of the session bearer. Initially request no `offline_access` and persist no provider refresh tokens. Application sessions need independent idle/absolute expiry, explicit revocation and account-active checks. Do not derive session lifetime from ID-token lifetime or silently renew past the application maximum. Provider SSO cookies remain a separate layer.

The owner must approve concrete lifetimes, refresh/reauthentication behavior, credential-change policy and the tolerated delay for provider-only changes before implementation. Back-channel notifications improve propagation but do not by themselves establish a hard maximum delay. That requires a reviewed reconciliation/freshness policy and observed provider behavior. Authentication failure must deny protected access; dependency failure must not create an anonymous or development identity.

## Proof required before claiming the selected provider works

1. Obtain owner-approved tenant/region, feature entitlement, spending limit and synthetic test accounts; configure a confidential client and explicit TLS callback/logout URLs. No production tenant or AWS provisioning is implied.
2. Capture reviewed provider configuration without secrets. Verify discovery issuer, client authentication, PKCE, key rotation, exact callback binding, signed claims, nonce/code replay, expiry, clock skew and safe outage handling.
3. Observe email verification/recovery and password login. For passkeys and step-up, record actual signed assurance/freshness results, remembered-MFA behavior, same-subject binding and failures. No security decision based only on requested `acr_values`.
4. Exercise two devices; local logout, logout-all, provider logout, password change/reset, provider block/unblock, application disable and provider session deletion. Measure delays, lost/duplicate notifications and reconciliation behavior. Prove old local sessions remain invalid after re-enable.
5. Keep provider integration evidence separate from synthetic protocol tests and CI PostgreSQL proofs. If access or feature entitlement is missing, mark the corresponding provider acceptance test **not run**.
6. Before implementing any visible authentication journey, perform the user's fresh targeted Mobbin research. This proposal authorizes no screens.

## Owner decision requested

Approve or amend the preferred Auth0 EU/Enterprise direction, provider-independent server-session design, initial database-connection method, and the separately specified session/security policy. Approval of an engineering direction does not purchase a plan or accept data-processing terms. Supplier cost, lawful processing/retention, sandbox access, permanent login domain and operational ownership remain explicit follow-ups before real users.
